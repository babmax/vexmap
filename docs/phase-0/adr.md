# Фаза 0: решения (ADR)

Факты и источники лежат в [audit.md](audit.md). Фаза 0 закрыта 2026-11-08: все решения ниже приняты владельцем, итог в
[README.md](README.md).

## ADR-001. Архитектура под 5000+ игроков

**Статус: принято владельцем 2026-11-07, вариант A (регионы за Velocity).**

Контекст: один сервер Horizon держит около 50 игроков при 20 TPS, план самого Horizon 200 на 8 ядрах.

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Регионы мира на отдельных серверах за Velocity** | Реально даёт 5000+. Прокси поддерживается штатно. Карта, страны и история едины | Переход между регионами выглядит как смена сервера. Плотность игроков в одном месте ограничена |
| B. Один сервер и лимит игроков | Просто и бесшовно | Потолок 50 сегодня, возможно 200 позже. Цель 5000 снимается |
| C. Копии мира (каналы) | Просто масштабируется | Рушит RP: границы, войны и постройки разные в каждой копии |
| D. Свой параллельный движок с бесшовным миром | Настоящий единый мир | Отдельный огромный проект в ядре Horizon, не сводимый к моду |

**Рекомендация: A.** Начать на одном сервере, код с первого дня писать так, будто серверов много: идентификатор региона в
каждом событии, единая шина и база данных, никакого общего состояния в памяти игрового сервера.

Последствия, которые надо принять осознанно:

- Сражение ограничено ёмкостью сервера региона. Битва на 500 игроков в одном месте при текущих 50 на сервер невозможна.
  Это влияет на дизайн войн: фронт должен быть распределённым, с лимитами на контрольной точке.
- Регионы нужно проектировать заранее, деление столицы или популярного города на два сервера будет больно.
- События войны и торговли между серверами идут через шину, а не через игровой тик.
- Если Horizon выполнит план на 200 игроков, серверов станет меньше без смены архитектуры.
- **После S5b:** настоящая передача работает через модуль `[transfer]` и Velocity: 8 передач из 8, около 0,64 с, вещи и позиция
  следуют за игроком ([spikes.md](spikes.md)). Для боевого варианта нужен плагин Velocity или свой прокси, а бой и массовый
  переход на границе ещё не проверены. Это теперь главный открытый риск ADR-001.

## ADR-002. Форк клиента

**Статус: принято владельцем 2026-11-08, форк не делаем. Решение 135 остаётся запасным.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Без форка: клиентский мод плюс PR, миксины как временная мера** | Обновления Horizon дешевле, реестр и лончер работают | Сборка у игрока, зависим от приёма PR |
| Форк сразу | Полная свобода, свои готовые сборки | Постоянная синхронизация с очень быстрым апстримом, API растёт почти каждый день |

**Рекомендация: форк не делать.** Прототип S1 подтвердил запуском: глобус рисуется через `native_hand_drawn` поверх мира и под
HUD, цена примерно 0,1–0,3 мс GPU на RX 570 ([spikes.md](spikes.md)). Условие решения 135 («нельзя через хуки») для глобуса не
выполнилось. Прототип S2 показал то же для панорам. **Форк клиента не нужен ни для одной проверенной функции.** Решение 135
вернётся в силу, только если Horizon откажет в нужных PR, а временные миксины перестанут работать.

Правило 11 промта требует только именованных хуков. Предлагаемое исключение: пока PR не принят, разрешить миксин на внутреннюю
функцию, с пометкой и ссылкой на PR. Официальный Minimap делает так же.

## ADR-003. Транспорт данных

**Статус: исходный вариант с `mod_net` заменён после S5, см. ниже.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **`horizon:mod_net`, ограниченная очередь, sidecar отдаёт данные через тик** | Нет лишних портов, тот же игровой канал, авторизация уже есть | Всё идёт через тик. Лимиты на сообщение. Проход через Velocity не проверен |
| Отдельный канал от sidecar к клиенту | Разгружает тик, удобен для тяжёлых потоков | Новый открытый порт, токены, отдельная защита от DDoS |

**Решение пересмотрено после S5: plugin channel, а не `mod_net`.** Статус: принято владельцем 2026-11-08.

`mod_net` хорош на прямом соединении (18,75 МБ/с без потерь), но через Velocity не работает: сервер видит клиента не как
`horizon` и молча не отправляет сообщения. По ADR-001 игроки всегда идут через прокси, поэтому основной транспорт такой:

- Сервер: `native_send_custom_payload_to_player`, до 1 МиБ за сообщение, без лимита на тик.
- Клиент: хук `client_packet` на приём, `native_send_packet` на отправку, до 32 767 байт. Регистрация каналов `minecraft:register`.
- Подтверждено запуском на 15,6 КБ/с, включая 6 переходов между серверами ([spikes.md](spikes.md)).

Что это значит для кода:

- Лимитов нет ни у какой стороны, контроль потока, повторы и разбиение на части полностью наши.
- Хук приёма на сервере `native_custom_payload_from_client` пока не в каталоге именованных хуков. Его надо предложить в
  каталог через PR, до этого он цель миксина с исключением из правила 11.
- Параллельно предложить PR в Horizon об определении Horizon-клиента за прокси: тогда снова заработают `mod_net`, допуск и
  другие функции. Отправлять PR только с согласия владельца.

Отдельный порт по-прежнему не нужен.

## ADR-004. Источник данных для тайлов

**Статус: принято владельцем 2026-11-08 при закрытии Фазы 0.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| `native_read_columns` на сервере | Официальный API | Только загруженные чанки, работает на тике. Принудительная загрузка рассчитана на десятки чанков, а не тысячи |
| Снимки клиентов (`native_client_chunks`) | Официальный API, фоновые потоки | Клиентам нельзя доверять, охват случайный |
| **Sidecar читает файлы региона с диска, изменения приходят из `native_block_changed`** | Весь мир и никакой нагрузки на тик. Крейт `horizon-world` (MIT) уже читает файлы `.mca`, все кодеки и палитры | `horizon-world` рассчитан на офлайн-вход: чтение файла во время записи сервером не поддерживается. Хук не видит прямую запись в хранилище |

**Рекомендация: чтение файлов sidecar-ом через `horizon-world`**, для живых изменений `native_read_columns` небольшими
порциями по очереди грязных чанков. Хук `native_block_changed` только ставит флаг, O(1).

Гонку с записью решаем так: тайлер читает чанк повторно, если декодирование или контрольная сумма не сошлись, а полный обход
идёт по копии мира из резервной копии. С регионами (ADR-001) у каждого сервера свой sidecar-читатель, результат идёт в общее
хранилище тайлов. Надо ли при таком подходе соглашать чтение с сохранением мира, покажет прототип.

## ADR-005. Панорамы

**Статус: принято владельцем 2026-11-08 при закрытии Фазы 0.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **PR с рендером второго вида вне экрана** | Фоновая съёмка без рывков, полезно другим модам | Работа в ядре, ждём приёма, вторая отрисовка мира стоит дорого |
| Съёмка в основной кадр через `native_camera_pose` | Работает без PR | Заметный рывок примерно раз в 3 секунды. Неприемлемо |
| Съёмка только в момент бездействия или по запросу | Без рывков и работы в ядре | Панорамы покрывают дороги медленно, не каждые 16 блоков |

**Решение после S2: подмена кадра через существующий путь скриншотов, с одним небольшим PR.** Второй проход рендера писать не
нужно: `draw_scaled_frame` уже рисует кадр в отдельную текстуру, окно сохраняет прошлый кадр. Съёмка подтверждена запуском,
стыки граней сходятся ([spikes.md](spikes.md)).

Для боевого мода нужен именованный хук вместо подмены внутренней функции `Renderer::screenshot_size`. PR небольшой, отправка только
с согласия владельца, а до его приёма действует исключение из правила 11. Между гранями обязателен промежуток в несколько кадров.
Запасной вариант, съёмка только в моменты бездействия, остаётся на случай, если задержка окажется заметной на средних ПК.

## ADR-006. Круглая граница и проекция

**Статус: принято владельцем 2026-11-08 при закрытии Фазы 0.**

Ванильная граница квадратная. Вариант: сервер считает круг вписанным в квадрат, а за пределы круга игрока не пускает сам мод
(проверка в `player_tick`, с лимитом на тик). Углы квадрата станут недоступными. Если хотите углы оставить как запретную зону
без наказания, скажите на этапе Фазы 5.

Сравнение проекций (мир уже диск, что упрощает задачу):

| Проекция | Швы и особые точки | Искажения | Тайлы |
|---|---|---|---|
| Equirectangular | Шов и два полюса | Большие у полюсов | Простые, но диск ложится плохо |
| Cube-sphere | 12 рёбер куба | Небольшие | Сложнее, шесть граней, диск режется |
| **Азимутальная равнопромежуточная на сферический сегмент** | Шва нет, центр гладкий, край один | По радиусу нет, по окружности `sin θ / θ` | Тайлы остаются в координатах мира, проекция в вершинном шейдере |

**Рекомендация: азимутальная.** Формулы: `θ = (r / R) · θ_max`, долгота равна углу вокруг центра мира, обратное преобразование
тривиально. Остальная часть шара оформляется как океан.

Масштаб по окружности у края [оценка]: `θ_max` 90° даёт 0,64, 120° даёт 0,41, 150° даёт 0,19. **Начальное значение 120°**, по
виду можно настроить. Плоские режимы показывают истинную геометрию, а расчёты расстояний всегда идут в плоскости мира.

## ADR-007. Допуск только Horizon-клиентов

**Статус: принято решением 132, механизм принят 2026-11-08.**

1. **Поправка после S5:** `horizon-clients-only = true` за Velocity не работает, отказ получает и настоящий клиент Horizon. На
   серверах за прокси он выключен. Без него прямой вход всё равно закрыт: forwarding отклоняет подключения в обход прокси.
2. Сервер мода ждёт рукопожатие по `mod_net` (версия протокола карты) несколько секунд после входа, иначе `native_kick` с понятным
   сообщением и ссылкой на инструкцию.
3. Это защита от ошибки, а не от взлома. Безопасность по-прежнему держится на проверках сервера (правило 8).

## ADR-008. Ресурс-пак

**Статус: принято решением 133, механизм принят 2026-11-08.**

`native_send_resource_pack` с хэшем SHA-1 и `required`, ответ через `native_resource_pack_status_v2`, при отказе `native_kick`.
Пак лежит на статическом хостинге.

По `resource-packs.md` серверные паки в клиенте работают: подсказка, загрузка до 250 МиБ, проверка SHA-1, удаление при выходе.
Ограничения для нашего пака:

- **Шрифты TrueType не поддерживаются**, только `bitmap`, `space`, `unihex` и `reference`.
- **Шрифт, выбранный в текстовом компоненте, игнорируется**, рисуется шрифт по умолчанию. Поэтому иконки в заголовках меню
  кладём глифами в личной области Unicode через провайдер `bitmap` в `font/default.json`.
- **Масштабирование спрайтов GUI работает только через `nine_slice`**: `tile` и `stretch_inner` не читаются.
- **Смена региона:** пак удаляется при выходе с сервера. Если переход через Velocity вызывает перезагрузку ресурсов, каждый
  переход станет заметно дольше. Проверяется в прототипе S5.

## ADR-009. Онбординг игрока

**Статус: принято владельцем 2026-11-08 при закрытии Фазы 0.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Реестр и лончер, плюс подробная инструкция и проверка готовности на сервере** | Штатный путь, доверие через ревью | Долгая первая сборка. Каждому игроку показывается красное предупреждение |
| Своя готовая сборка клиента | Вход в один клик | Фактически форк: подпись, обновления, недоверие к бинарнику |

**Рекомендация: штатный путь.** Его цена на тысячах игроков реальна, поэтому после S6 проверяем цифры. Если они окажутся
неприемлемыми, вернёмся к варианту со сборкой.

## Бюджеты (черновик)

Все значения пока не измерены. Базовая машина игрока: 4 ядра, 16 ГБ ОЗУ, GPU уровня GTX 1650 или RX 570.

| Показатель | Бюджет | Основание |
|---|---|---|
| Нагрузка мода на тик, p99 | < 0,5 мс | Промт, 1 % от 50 мс |
| Задержка маркера игрока | < 1 с | Промт |
| Открытие карты | < 1 с | Промт |
| Карта при 5000 маркерах, пресет «Баланс» | 60 FPS | Промт. Маркеры одной страны, остальное кластеры |
| Трафик карты, средний | 16 КБ/с на игрока | [оценка] Около 20 % от игрового |
| Трафик карты, пик | 64 КБ/с на игрока | [оценка] С разгрузкой и отбрасыванием устаревшего |
| Панорама | Около 200 КБ | [оценка] 1000 км дорог дадут 62 500 панорам и 12,5 ГБ без дедупликации |

Позиции: 10 байт на игрока при 2 Гц дают 4 КБ/с на страну из 200 онлайн и 20 КБ/с на 1000 онлайн. На больших странах нужен
учёт видимой области и кластеры.

## Обновлённый план фаз

- **0b. Новая:** прототипы S1–S6 из [audit.md](audit.md). По итогам пересматриваем ADR-002, ADR-003, ADR-005, ADR-009.
- **1.** Конвейер сборки и CI. Объём заметно меньше исходного: большинство хуков уже есть, PR нужны точечно.
- **3.** Realtime-слой сразу в варианте со многими серверами.
- **9.** Панорамы зависят от ADR-005, поэтому риск по срокам выделен отдельно.
- **11.** Дизайн-документ войны учитывает лимит на сервер региона.
- **14.** Нагрузочный тест проводится на арендованном стенде, а не на домашнем ПК.

Относительный объём: Фазы 5, 9, 11 и 14 самые большие, Фазы 1, 4 и 15 средние. Календарную оценку дам после прототипов: сейчас она
была бы выдуманной.

## Оставшиеся риски

1. **Масштаб:** при 5000 игроках понадобится порядка 100 серверов, и бюджет с их администрированием реально большой.
2. **Скорость апстрима:** API растёт очень быстро, CI должен проверять совместимость постоянно.
3. **Онбординг:** сборка на компьютере каждого игрока может отпугивать людей сильнее любой технической проблемы.
4. **Выкатка всего сразу:** при таком объёме риск велик. Выключатели модулей снижают его, но не убирают.
5. **Доверие:** нативный мод работает с полными правами на компьютере игрока, поэтому открытый код и подпись обязательны.
